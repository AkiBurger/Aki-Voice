## 零、总原则

**每一环都用该领域更强的工具，而不是最方便的那个。**

大多数同类开源项目是"抓一个模型，包一层界面"。本项目对每一个环节单独做过选型，并且**同一环节保留备选实现**，以便横向对比。

**架构上的落实**：每一环做成"可替换的插头"，工具名不写死在业务代码里。

```
pipeline/
├── 切分/     ├─ fsmn_vad.py      默认
│             └─ 简单音量切分.py    备选
├── 识别/     ├─ funasr.py        默认
│             └─ whisper.py        备选
├── 质检/     └── ...
├── 打分/     └─ eres2net.py
└── 引擎/     ├─ gpt_sovits.py    默认
│             └─ （预留其它引擎位置）
```

## 一、语音识别（ASR）—— 差距最大的一环

### 数据

来自 [GigaSpeechBench](https://github.com/SpeechColab/GigaSpeechBench)（真实场景多语言识别测试榜，数字越低越好，加粗为本项目选择）：

| 模型 | **日语** | 中文方言 | 粤语 | 中文（专业领域） | 英语 |
|---|---|---|---|---|---|
| **FunASR** | **25.44** | **22.79** | **6.13** | **3.12** | 6.95 |
| Whisper-large-v3 | 39.28 | 60.45 | 39.75 | 9.83 | 8.79 |
| Qwen3.5-Omni-Plus | 27.36 | 27.22 | 7.94 | 3.36 | — |
| GPT-4o 转写 | 44.34 | 62.15 | 19.29 | 15.29 | 23.36 |
| Gemini 3.0 Flash | 39.84 | 70.38 | 24.39 | 8.79 | — |
| ElevenLabs Scribe v2 | 29.95 | 56.08 | 32.09 | 5.24 | — |

### 结论

**日语场景下，FunASR 的错误率约为 Whisper 的 65%（25.44 vs 39.28）。中文方言差距更大（22.79 vs 60.45）。**

对做 galgame 配音而言这尤其重要 —— **日语音频 + 角色语气 + 可能有背景音乐**，正是 Whisper 最弱的场景。

### 具体选型：Fun-ASR-Nano-2512

来自 [ModelScope](https://modelscope.cn/models/FunAudioLLM/Fun-ASR-Nano-2512) / [HuggingFace](https://huggingface.co/FunAudioLLM/Fun-ASR-Nano-2512)，官方说明要点：

| 特性 | 说明 |
|---|---|
| 参数量 | 800M |
| 语言 | 中文、英文、日文 |
| 中文细分 | 7 种方言（吴、粤、闽、客家、赣、湘、晋）+ 26 种地方口音 |
| 特色 | 支持歌词识别、说唱语音识别 |
| **背景音乐场景** | 专门优化"音乐背景下的歌词识别" |
| 实际部署 | 支持 CPU（llama.cpp/GGUF）、支持 vLLM 加速（约 340 倍实时） |
| 体积 | 约 1.9 GB |

官方给出的行业场景对比（WER %，越低越好）：

| 场景 | Fun-ASR-Nano | Whisper-large-v3 |
|---|---|---|
| 复杂背景 | 14.59 | 32.57 |
| 方言 | 28.18 | 66.14 |
| 口音 | 12.90 | 36.03 |
| 歌词 | 30.85 | 54.82 |
| 远场 | 5.79 | 22.21 |

### 备选

- **Whisper-large-v3** —— 通用、生态最好，但本项目主场景（日语、方言）明显弱
- **Qwen3-ASR** —— 英语强，日语中等，可作对比项

## 二、语音活动检测（VAD）与切分

### 选型：FSMN-VAD

| 项 | 说明 |
|---|---|
| 来源 | FunASR 生态 |
| 体积 | 约 1.6 MB |
| 优势 | 专门做"这里是不是人声"，比按音量/静音切准得多 |
| 搭配优势 | 与 Fun-ASR 同属一个生态，兼容性最好 |

### 为什么不用 GPT-SoVITS 自带的切分

自带的切分基于音量阈值，规则简单：

- 背景有持续低噪时，会切不准
- 语速慢、停顿多的表演型语音（正是配音素材的特点）容易切碎

**FSMN-VAD 是模型判断，不是阈值判断。**

## 三、说话人检测与声纹比对 —— 质检里最值钱的一环

### 要解决什么问题

**一个数据集文件夹里混进了两个角色的声音，是相似度下降的隐形杀手。** 多数人不知道这一点，训完了只觉得"怎么不像"，找不到原因。

### 选型

| 用途 | 用什么 | 说明 |
|---|---|---|
| 说话人分离 | FunASR 生态的说话人分离能力 | 判断一段音频里有几个人在说话 |
| 声纹比对 | **ERes2NetV2**（`pretrained_eres2netv2w24s4ep4.ckpt`） | 提取声纹特征，算两段音频是否同一人 |

### 为什么用 ERes2NetV2

- **GPT-SoVITS 自己训练时就在用它** —— 说明它在这个任务上已被验证
- 项目内已自带（约 102 MB），无需额外下载
- 可直接复用同一套依赖

### 具体用法

```
参考音频（主角声纹）
      ↓ 提取声纹特征
      ↓
逐段音频 → 提取声纹特征 → 算相似度
      ↓
低于阈值 → 标记"疑似混入其他说话人"
      ↓
交用户在数据地图上确认
```

## 四、文字纠错 —— 用本地大模型

### 选型：本地语言模型（Ollama + Qwen3）

| 项 | 说明 |
|---|---|
| 来源 | 用户本机已安装的 Ollama |
| 模型 | Qwen3（约 5 GB） |
| 优势 | **完全本地，音频和文本都不出本机** |

### 做什么

不只用识别置信度判断，**还结合"这句话的长度合不合理"**：

```
输入给模型：
  "这是从日语音频识别出的文字，可能有错。
   音频长 2.3 秒，这句话念完大概要多久？
   有哪里明显不对？给出修改建议。"

模型输出：
  "2.3 秒念不完这句，可能有漏字。
   另外「きて」在这个语境更像「来て」"
```

**这比单纯看识别置信度准得多** —— 因为它能发现"这句话根本念不完"这类结构性错误。

### 降级策略

**这一环是可选的。** 用户不装这个模型，基础流程照样能跑，只是少了 AI 建议，只能靠置信度筛可疑项。

## 五、声音合成与训练引擎

### 选型：GPT-SoVITS

| 项 | 说明 |
|---|---|
| 状态 | 本机已装，权重齐全（v2Pro / v2ProPlus / v3 / v4） |
| 语言 | 中文、英文、日文 |
| 日语优势 | 自带日语词典（`ja_userdic`）与日语优化 |
| 训练能力 | 支持 GPT + SoVITS 双模型微调、支持 LoRA |
| 调用方式 | 提供 HTTP 接口（`api_v2.py`），也可直接调训练脚本 |

### 为什么先不换

| 候选 | 为什么暂不用 |
|---|---|
| IndexTTS-2.5 | 更新、跨语言更强，但需要 Python 3.11 且要求 CUDA Toolkit ≥12.8，本机均不满足，需额外安装 |
| CosyVoice3 | 评测分数高，但不支持日语 |
| Fish Audio S2 Pro | 参数量大，8 GB 显存吃紧 |

**留活口**：引擎通过接口调用，将来想换只需新增一个适配文件，界面不动。

### 训练参数：哪些真正影响相似度

| 影响等级 | 参数 | 说明 |
|---|---|---|
| 🔴 决定性 | 数据干净度 | 混入他人声音、BGM 残留、爆音 —— 第一杀手 |
| 🔴 决定性 | 有效数据量 | 5 分钟及格、30 分钟舒服、2 小时以上可分情绪 |
| 🔴 决定性 | 标注文本准确度 | 错一个字就是教模型念错，音色韵律一起歪 |
| 🔴 决定性 | 模型版本 | v2Pro 稳、v2ProPlus 更像、v4 实验性 |
| 🟠 重要 | 总轮数 | 唯一"多了少了都坏"的参数，与数据量反相关 |
| 🟠 重要 | 存档策略 | **必须保留多个存档**，否则无法对比轮次 |
| 🟡 次要 | 每批数量 | 多半是显存开关，过小会训练不稳 |
| ⚪ 不用碰 | 学习率、保存频率、DPO | 官方已调好，动了大概率更差 |

**结论**：
- 数据干净度、数据量、标注准确度是**决定性的三项**，占相似度的大头
- 模型版本与总轮数是**唯一值得动的两个训练参数**
- 其余要么没影响，要么一动就更差

**因此本项目不做"自动搜索参数"。** 已确定（见 [`03-开发计划.md`](03-开发计划.md) Q1）：
8 GB 显存下试 3 组要 3 小时，收益不如把数据洗干净。
改为**保留训练过程中的多个轮次存档 → 自动评分分类 → 留好的几版让人挑**。

## 五之二、情绪控制怎么实现（重要澄清）

### 先说结论：GPT-SoVITS 没有独立的情绪参数

查证官方推理代码（`inference_webui.py`）后确认，它的推理参数里有：

| 参数 | 作用 |
|---|---|
| `top_k` / `top_p` / `temperature` | 采样控制，影响稳定性与变化度 |
| `speed` | 语速，范围约 0.6 ~ 1.65 |
| `sample_steps` | 采样步数，v3/v4 用，越高越慢越精细 |
| `if_sr` | 超分辨率 |
| `pause_second` | 句间停顿时长 |
| `rep_ref`（多参考） | **上传多个参考音频，音色融合** |
| `ref_free` | 无参考文本模式（v3 不支持） |

**里面没有"高兴 / 悲伤 / 生气"这样的情绪参数。**

### 那情绪是怎么来的

**靠参考音频本身的语气。** 你喂给模型一段"笑着说"的音频，它就学着用那个语气说；喂一段"哭着说"的，它就带哭腔。

```
参考音频（带情绪）  →  模型模仿 → 输出同样情绪
```

也就是说：**情绪 = 换一段参考音频。**

### 所以本项目要这么设计

**原则：参考音频从"用户的操作"变成"软件的内务"。**

用户不选参考音频，界面上也不出现这个步骤 —— 软件根据判断出的语气，自己从训练数据里挑一段对应的片段。

**训练完成后自动做一遍归类**：

```
扫描全部训练数据
   ↓
逐段判断语气（平静/开心/悲伤/生气…）
   ↓
每种语气挑出最典型的 1~3 段
   ↓
存成这个音色的"语气片段库"（内部数据，用户不用管）
```

**合成时**：

```
输入文本
   ↓
本地大模型判断该用什么语气
   ↓
界面显示判断结果（用户可改）
   ↓
软件从语气片段库里挑对应的片段
   ↓
连同文本一起送给模型
   ↓
输出带这个语气的语音
```

### 这个设计带来的要求

| 要求 | 说明 |
|---|---|
| **训练数据要保留情绪片段** | ⚠️ 质检阶段不能把情绪强烈的段当"异常"全剔掉 —— 这些最值钱 |
| **归类要自动** | 用户不参与，所以必须自动跑 |
| **判断要能容错** | 判错了一键换语气，不能让人从头再来 |
| **数据是硬前提** | 数据里没有的情绪，软件变不出来 |

### 关于"高数据拟合"

这是本项目情绪能力的根本依赖：

| 数据情况 | 能出来的效果 |
|---|---|
| 丰富、情绪起伏多 | 能挑到笑声、哭腔、怒气，语气自然 |
| 平淡、全是念白 | **挑不出情绪** —— 数据里本来就没有 |

**这一点必须写进 README**，避免用户以为"装上软件就能随心所欲加情绪"。

### 已确定的决策

- ✅ **方案丙**：自动判断 + 用户可改
- ✅ **用户不接触参考音频**：软件自动挑，界面不出现
- ❌ **不做**自动生成多版情绪让人挑（增加数倍耗时，收益不明显）
- ⬜ 情绪判断用什么实现（Q6，待定，不阻塞第一期）

## 六、相似度评测 —— 把"像不像"变成数字

### 选型：ERes2NetV2（同第三节）

```
训练完成
   ↓
用训练数据之外的 N 句测试文本合成
   ↓
用声纹模型比对合成音频与原始音频
   ↓
每句得 0~1 分，取平均
   ↓
排序 + 给出人话结论
```

### 设计要点

- **测试句必须未参与训练** —— 否则是在考背过的题
- **数字是参考，耳朵是裁判** —— 所以界面里"试听"和分数同等醒目
- **保留历史得分** —— 同一音色多次训练，能看出趋势

### 一个必须承认的局限

相似度分数的上限由**数据**决定。软件能把参数、版本、流程做对，但素材不行就是不行。

**这一点必须写进 README**，避免用户误以为"用了这个软件声音就一定像"。

## 七、Python 环境管理

### 为什么需要管这件事

新用户下载项目后，如果要求他手动装一整套 Python 环境，"下载就能用"就彻底没戏了。

### 策略：三级检测

```
启动
  ↓
① 检测到已有 GPT-SoVITS 环境？
   有 → 直接复用（作者本人属于这种情况，零等待）
  ↓ 没有
② 检测到本项目已有独立环境？
   有 → 直接用
  ↓ 没有
③ 自动创建（约 10 分钟，一次性）
```

### 工具：uv

| 优势 | 说明 |
|---|---|
| 快 | 比 pip 快很多 |
| 能装指定版本 Python | 不依赖用户预装的 Python 版本 |
| 项目管理 | 自带依赖锁定，别人装出来的环境一致 |

### 版本注意

不同环节对 Python 版本要求不同，**必须分别管理，不能混装**：

| 组件 | 版本要求 |
|---|---|
| GPT-SoVITS | Python 3.10 ~ 3.11（官方锁定 < 3.12） |
| FunASR | 较宽松 |
| **现有环境实测** | Python 3.13 + torch 2.11.0+cu130（可用） |

**教训**：不能盲目执行"自动装最新版"，否则会装出一个依赖不兼容的环境。**版本必须锁死。**

## 八、明确排除的技术

| 排除项 | 原因 |
|---|---|
| 语音人声分离（去 BGM） | 当前阶段不做。若素材本身干净则完全不需要 |
| 修改模型内部架构 | 收益低、成本高。在单张 8 GB 显卡和数据有限的条件下，改架构远不如把数据、版本、轮数做对 |
| 云端 API 识别 | 音频要上传，涉及隐私和成本 |
| 端到端大模型 TTS | 8 GB 显存吃紧，且不支持微调训练，无法"让声音更像" |
